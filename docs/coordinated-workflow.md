See [capacity compatibility](migrations.md#guarded-200k-joint-evidence-exception-2026-11-09).

An exclusive v2 clarification stop can now enter a one-pass, Play-owned evidence-only
inspection stage before comparison planning. Each full original and support is read
with all counterparts and pinned answers; observations flag conservative joint sets,
never verdicts. Resulting groups must preserve every flag and receive exact-body
read/check turns before ordinary full verification. No attempt/usage reset or approval
is inferred. See [inspection compatibility and limits](migrations.md#evidence-first-blocked-lookup-inspection-2026-11-09).

Oversized lookups with non-pinned counterparts can now receive one charged, explicit
model scope clarification under Play. Confirmation schedules each requested original

product choice is inferred, and genuine joint requirements still block. See
[lookup clarification v2](migrations.md#counterpart-preserving-lookup-clarification-2026-11-09).

Real joint evidence is never split merely to fit. Play now first tries v10 lossless
literal phrase pooling, retaining every exact body/support and all pinned answers in
the same joint packet. Existing paid work, attempts and full verification are unchanged.
Incompressible joint evidence still stops honestly. See [lossless joint packing](migrations.md#lossless-joint-evidence-phrase-pooling-2026-11-08).

An oversized lookup whose explicit counterparts are only the always-pinned human
answers can now enter a bounded, charged model clarification. The model must explicitly
confirm separate original-unit retrieval before packing can split that request; it

or weakens mandatory verification. See [lookup clarification compatibility](migrations.md#oversized-pin-relative-lookup-clarification-2026-11-08).

## Progress-based technical correction (2026-11-08)

work. Beyond the first two corrections, verification must identify a distinct existing
draft target/current human-evidence comparison, with the full originals supplied.
Unchanged corrections, repeated comparisons and exact earlier target versions stop.
Unrelated draft actions remain intact; genuine conflicting intent still needs review.
Every accepted correction restarts complete verification. Eight total repairs and the
unchanged overall request, failure, page and storage ceilings bound processing; no

Play can recover a completed shared-answer reply rejected solely by the old aggregate
output reserve. It validates the exact original prompt/model/completion and no-tools

no-progress safety stop is not reset to make another repair request. See
[output capacity and no-inference recovery](migrations.md#shared-answer-output-capacity-and-completed-reply-recovery-2026-11-08).

## Simple processing (2026-11-08)

The primary controls are **Play**, **Pause**, **Stop**. Play starts/resumes saved
specification work using the selected AI connection. Save product answers, then Play
to process that saved set. Pause allows the current reply to be saved before waiting;
Stop immediately cancels the owned request and disarms the coordinator. Both retain
completed work and usage. Reload/restart never starts work. The previous controls,
run accounting and recovery details remain under collapsed **Processing details and
advanced actions**, not in the ordinary workflow. Coding, scanning and web research
remain separate operations.

Play adopts compatible current-revision **shared-answer** checkpoints in place,
including the reported exhausted final evidence lookup. The original plan, paid
receipts, spent attempts and historical checks are not reset. Technical source/scope
and missing-original preparation can be handled at adoption without separate user
consent. Existing original requirements may be revised across feature boundaries
only when justified by the concrete original answers and complete detailed support.
New out-of-feature records, withdrawals, inferred conflict precedence and approvals
remain prohibited. Every original batch verifies again after an actual repair.

Useful shared lookups no longer exhaust a four-request repair allowance. The internal
Play policy reserves total requests before dispatch, with a 256-request task safety
ceiling and three consecutive unsuccessful validation/request reservations. Accepted
useful replies clear the consecutive-failure count, not total usage. Pause/Stop/reopen
and repeated Play cannot renew a task safety stop. Legacy work retains two repairs;
explicitly adopted progress-based work uses the distinct-comparison gates and finite
eight-total-repair backstop above. Packet, storage and page guards remain. A run-wide 256-request ceiling also prevents an
unbounded coordinator episode. These are safety checks, not new user authorizations.

**Implemented boundary:** shared-answer adoption and new shared work use the new
policy. Legacy individual-answer, assessment, refinement and other specialized
engines keep their existing durable retry semantics; they can still stop for
technical failures requiring advanced inspection. Unclassified model blockers,
unavailable evidence, real human conflicts, provider errors and genuinely unfit
inputs are not silently overridden. This slice does not claim universal recovery
or live model correctness. See [upgrade and qualification](migrations.md#play-owned-specification-processing-2026-11-08).

Compatible shared packing stops can be resumed through **Continue specification**
even when originally started by separate response processing. The whole saved
cohort must remain intact, and explicit continuation must prove exact current-input
compatibility and fit before requeueing anything. A visible offer is not approval
or a fresh retry allowance; real failures and human blockers remain stopped. See
[standalone continuation compatibility](migrations.md#separately-started-shared-packing-continuation-2026-11-08).

A saved read can now continue when its whole exact comparison fits the current
96,000-character input bound but speculative space for a maximum future draft does
not. Normal pages retain draft headroom; a tight indivisible unit stays alone with
the full current draft, all answers and complete support. Later inputs are measured
again and can still genuinely block. All verification remains mandatory. Use
ordinary **Continue specification**, not reset or a new grant. See
[tight read compatibility](migrations.md#measured-current-draft-read-units-2026-11-08).

## Repeated evidence-request recovery (2026-11-07)

may retain a provisional no-change draft until later evidence permits a change;

records a one-time allowance and corrected layout, starts no AI work and preserves
the original four requests. The next request is attempt five, not a fresh attempt
one; it consumes AI plan usage. The extra allowance cannot be renewed or stacked

The recovery transaction must prove that requested bodies actually move into the
next bounded input; it does not simply extend an unchanged loop.

## Bounded shared-draft repair (2026-11-06)

A negative shared-answer check no longer strands an otherwise usable saved answer
group. The engine retains the rejection and original answers, asks for a complete
corrected draft using that feedback and exact evidence, then checks **every** original
evidence batch again. Original reading steps are retained rather than repeated. The
queue explicitly shows repair versus verification progress; check progress may move
back because earlier checks do not verify a changed draft.

There are at most two accepted draft repairs per original group. Repair requests also
use the existing charged four-attempt step ceiling; Pause, failure, Continue and clone
adoption cannot refund it. Invalid output, timeouts and newer input still stop work.
Feedback does not establish product intent: genuine conflicting/ambiguous human choices
must return an explicit blocker with the precise choice needed, never guessed precedence.
That blocker remains a human-review stop; automatic targeted-question creation for
shared blockers is not implemented by this repair slice.

Existing saved rejected groups can use **Continue specification** after updating.
Explicit continuation recovers only this coordinator's eligible unfinished group,
including older passes incorrectly marked completed after interruption. Startup makes
no calls; no answers need re-entering. Exact material changes still block incompatible
reuse instead of silently rewriting old work. Repair evidence survives portable adoption;
older app versions reject new repair variants and should be updated before opening them.
See [migration and recovery details](migrations.md#bounded-shared-answer-draft-repair-2026-11-06).

Shared lookup requests now explicitly distinguish already detailed bodies from missing
evidence. The per-request response schema allows only the missing original IDs, not
every ID in the overall task inventory, and omits lookups when nothing is missing.
This is dispatch guidance, not weaker validation: unavailable, duplicate and repeated
loads still stop atomically with distinct explanations, and all spent attempts remain

## Continuous work windows and processing diagnostics (2026-11-06)

passes/sixteen request attempts, and the five-active-minute checkpoint is cooperative:
finish the in-flight request (or ordinary package), then yield between completed steps.

An intentional staged request/time-budget pause with accepted steps can resume in the

The later shared-draft repair slice above adds a separate bounded corrective stage
for negative draft verification; it is not replay of an unchanged rejected check.

Collection still ends at the soft question target, a human-review decision, saved
input, or no eligible work. Continuous consent is not proof of completeness, approval,

Startup never arms the scheduler; explicit continuation adopts policy 2 and projects

pair later in the submitted set. This does not authorize cross-feature or scoped grouping.
New epic job diagnostics distinguish a new package from an incompatible saved check

## Bounded question collection (2026-11-06)

This describes policy 1, superseded for newly authorized continuous runs by policy 2
above. Existing original evidence, task identities and retry ceilings remain valid.

New explicit continuous **Continue specification** runs now collect a small question
batch instead of stopping immediately after one workflow package produces a question.
When discovery starts with no waiting decisions, it follows existing eligible epic
packages toward a **soft target of five pending questions**. An exact, unfinished
collection can resume after Pause/restart under explicit continuation, even if its
earlier completed packages already produced questions. Existing waiting batches are
not automatically enlarged merely by adopting this scheduling policy.

Each collection is limited to **five package passes, sixteen actual model request
attempts and five active minutes**, whichever ends first. A package pass includes an
explicit retry or no-call eligibility pass; interrupted work does not get a fresh
package counter. Before starting another package the scheduler conservatively reserves
three requests for the existing ordinary retrieval protocol, so it may stop with up
to two unused request slots. Staged reads/checks count individually inside the same
sixteen-request ceiling and retain accepted steps and the original per-step retry
limits. Partial staged proposals do not publish when the collection budget ends.
The surrounding workflow remains continuous; these are question-collection bounds,
not a new whole-workflow cutoff or an allowance for automatic retries.

Collection stops sooner for saved input, proposals needing review, technical failure,
Pause, changed inputs, or no other eligible packages. Only packages the existing
engine considers eligible may continue past a question; dependency/source-linked or
global questions still hold their related packages. This is structural scheduling,
not proof that topics are semantically independent. All useful final-package questions
are retained above the target; empty results are allowed and no question is forced
to fill a quota. Smaller batches are valid. Area assessments, approvals and coding
are not introduced into collection.

The queue shows ready-question count, package/request usage and the saved time budget.
Saving responses after collection still makes no AI calls; **Submit saved responses**
captures them for integration. Responses saved while a package is running stop further
packages and wait for separate submission. The original question, evidence, package
identity and saved paid work remain authoritative. New product input is not silently
chased during collection; changed inputs require explicit continuation. A completed
no-question eligibility pass establishes the existing discovery receipt only when
the entire reported scope is settled, with no waiting, blocked or unexamined work.
Neither reaching the target nor spending the budget establishes readiness.

SQLite **32 → 33** adds optional local policy/progress fields without rewriting old
grants, jobs, evidence, assessment dates, context identities or portable formats.
Startup never opts in or dispatches. Explicit recovery conservatively charges any
unaccounted active interval from a crashed collection rather than refunding a request's
time; a clean Pause records time and clears that interval. Collection consent and
counters are machine-local; exported package evidence follows its existing formats.
See [migration details](migrations.md#bounded-workflow-question-collection-2026-11-06).

This slice batches existing package discovery, not a new one-request multi-feature
question-generation protocol. It does not batch readiness clarifications, initial
interpretation or scoped manual discovery, tune question quality, broaden shared-answer
permissions, or qualify actual-user latency/semantic effectiveness.

## Shared answer integration (2026-11-06)

After **Submit saved responses**, the coordinator can integrate **two to five new,
concrete, unscoped answers in the same feature** together. Each original question,
options, answer and current source stays distinct and pinned in every request. The
complete mandatory evidence sets from the individual tasks are pooled without dropping
records; one collection pass builds a combined draft and one verification pass checks
that frozen draft against every evidence batch. Publication is atomic only after all
checks pass, with an explicit model outcome/explanation for each original submission.
Outcomes are model judgments, never human approvals. Existing automatic-activation
gates still require current authorizing answer sources and full original target support.

Reviews, targeted answers, delegated/deferred choices, research, pair-resolution work
and already-started individual work retain their established paths. Shared fit is checked
before dispatch; a group that cannot fit may use individual processing only before any
shared request starts. Once started, the original group, replies and attempts stay
bound together across Pause, failure, restart and portable continuation. A new grant
cannot turn paid shared work into fresh individual attempts. Later input remains in
the next batch. No partial changes, tools, organization/global interpretation, automatic
choice precedence or verification skipping is authorized. Indispensable joint evidence
must fit exactly or the group stops, rather than relying on separately read fragments.

Shared steps have four attempts each, up to 32 exact batches per phase, a 96,000-character
input cap and a 24,000-character draft reserve. Accepted exact lookups retain their
step/context identities; malformed attempts and cancelled calls stay spent. Completed
drafts survive failed publication and resume locally without another model call. Valid
replies arriving after an edit are saved historically before stopping stale. Changed
group inputs still require review: changed-material reconciliation, group-specific
exhausted-step extension and automatic clarification of rejected shared drafts are not
implemented. An old task is never silently abandoned to reset its allowance.

**Deterministic request comparison:** the same synthetic five-answer/nine-evidence-batch
fixture requires **90** individual read/check requests versus **18** shared requests,
with all original evidence retained. This is an 80% request-count reduction for that
fixture, not a measured live speedup, provider bill or semantic-quality qualification.
Additional exact lookups, incompatible scopes, smaller groups and larger drafts change
the actual cost. No real-project latency improvement is claimed yet.

Processing & queue shows the group's answer count and read/check progress; raw drafts
and receipts are stripped from browser snapshots. Logs count actual requests once.
SQLite 32 and conditional portable format 9 protect the new readers while leaving old
single-answer work untouched. See [upgrade details](migrations.md#shared-exact-answer-integration-2026-11-06).

## Question batches and fixed review checkpoints (2026-11-05)

On explicit Continue specification, the coordinator now collects answers/proposals
and related follow-up questions before reviewing definition validity. Pending
decisions hold **all** automatic area assessments, even structurally outside-scope
ones. A single answered question does not end the batch: related question discovery
runs first. A settled discovery pass with no pending decisions closes collection;
the existing change-impact/full-review sequence then reviews the accumulated changes.
This ordering supersedes the earlier automatic outside-scope scheduling below.
The dependency view remains navigation, not automatic review permission.
Compatible already-saved assessment/change-review work can resume directly on
explicit continuation; collection must not invalidate paid work by first generating
new questions against identical saved inputs.

**Review changes** in Processing & queue explicitly starts a bounded review-only
checkpoint (up to eight requests/five active minutes). Process saved responses first.
It can review the currently saved evidence while some questions remain unresolved,
without answering/approving them. It runs existing eligible impact checks/deeper
assessments, not input processing, conflict cleanup, broad discovery or coding. It
stops at completion or the existing allowance/failure boundary. Continue specification
can resume identical unfinished work under its normal displayed allowance.
Completion always pauses, including when unanswered questions remain: saving a
later answer cannot spend the leftover review-only allowance on processing/discovery.

Each checkpoint records its exact semantic input key (including global interpretation)
and original starting revision independently of assessment publication dates. Area
review publication does not change that key. New queued input or a product edit
